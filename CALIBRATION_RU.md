# CALIBRATION №4 — полный count и ограниченная выдача позиций

Статус: подготовлено до новых замеров №4. Результатов производительности №4 нет.
Никакой прогноз ниже не объявлен достигнутым. Первым коммитом этого отдельного
локального опыта фиксируются этот документ, входы, запросы, oracle и версии.

Профессионал: инженер, который исследует частый точный байтовый шаблон в неизменном
корпусе. Ему нужен точный общий count и только 10 разных координат, по которым
другой человек проверит байты. Сотни тысяч/миллионы координат передавать не нужно.
Эталоны реестра: GNU grep без индекса и Move-r как индексированная альтернатива.
Причина выбрать GLYPH должна быть измерена по времени и памяти этой операции;
готовый индекс, его загрузка и подготовка не объявляются бесплатными.

## Замороженные входы и договор результата

Те же публичные байтовые корпуса Git v2.49.0 (20 905 170 Б с разделителями) и
CPython v3.12.0 (59 431 090 Б). Коммиты, исходные SHA, карты и хеши готовых
релизных GLYPH/Move-r индексов — INPUT_LOCK.json. Деревья и кодеки не меняются.
Исходники пользователя 12inpunt и закрытые запросы здесь не используются.

Основной запрос — один байт `(`: Git 210 322 совпадения, CPython 804 292.
Независимо от движков заранее закреплены ещё `e`, `_`, пробел; все восемь пар
corpus/query остаются в опыте, даже если результат неудобен. Их прямые counts и
первые десять координат — QUERY_PLAN.json. Это подготовка oracle, не замер движка.

Результат: полный точный count с перекрытиями, `min(count,K)` различных нулевых
байтовых координат. Для K=10 допустимы любые десять настоящих совпадений, не
обязательно первые по тексту; выдаваемое подмножество сортируется численно.
K=0 означает точный count без координат. Для каждой координаты проверяются
диапазон и все исходные байты запроса. Служебные байты 00/01 в запросах запрещены
релизным профилем. Основные запросы однобайтовые, без LF; совпадений на стыках
файлов у них нет. Здесь flat concat-offset, без дополнительного №3 mapper.

Фиксированные controls в fixtures/: отсутствие, единственное совпадение, начало,
последний байт, перекрытия `aaaaa/aaa` и `ababa/aba`, UTF-8 байтовые смещения.
Не путать пустой результат с отказом. Пустой запрос и отрицательный K отклоняются.
Для публичных корпусов: подмена корпуса, ожидаемого SHA, запроса, count и координаты
должна отклоняться общим приёмочным проверяющим кодом. Сам поисковый GNU grep не
объявляется инструментом контроля SHA. Нативный поиск и экспериментальная обвязка
отмечаются раздельно. Любое неверное count/байты или принятая подмена блокирует
приёмку; сохраняем сырой FAIL и останавливаем основной замер до разбирательства.

## Готовые механизмы и GNU grep

Сначала используем существующий release GLYPH reader (count + ограниченный locate)
и готовый Move-r reader (query.num_occ + не более K next_occ), принятые в №3.
Их версии/бинарники/зависимости закреплены; RLB2 и переписывание reader не входят.
Новой зависимости или заимствования на этапе CALIBRATION нет. Лицензии и точные
флаги Move-r уже сохранены в приёмке №3; GNU grep 3.11 и coreutils 9.4 — системные.

GNU grep `-c` считает выбранные строки, а `-o` выдаёт неперекрывающиеся совпадения.
Поэтому `grep -c`, один `head -n10` и `grep -m10` не являются ответом на эту задачу.
Для основных однобайтовых запросов non-overlap совпадает с требуемой семантикой.
До замеров фиксируем ОБА корректных GNU-варианта:

1. Один проход: `LC_ALL=C grep -aFob -f query.bin corpus.bin`, потоковый reducer
   читает до EOF, считает все записи и хранит только первые K offsets. Не list()
   всего stdout и не досрочное закрытие по K. Время grep, pipe, reducer и bytecheck
   входит в операцию; внутренние переданные байты pipe считаются отдельно.
2. Два прохода: полный `grep -aFo -f query.bin corpus.bin | wc -l`, затем отдельный
   `grep -aFob ... | head -n K` для координат. Время обоих проходов, wc/head,
   запуска процессов и bytecheck включено. K=0 не запускает второй проход.
   SIGPIPE/141 во втором проходе допустим только после доказанно завершённого
   count-прохода и получения ровно min(K,count) правильных координат; иные ошибки
   не превращаются в PASS. No-match grep code1 — успешный нулевой результат.

Публикуем оба GNU-варианта. Сильнейший ориентир GNU для прогноза — меньшая
агрегированная медиана одного из двух целиком на данном корпусе; не выбираем
метод задним числом отдельно для каждого запроса.

Перекрывающиеся controls требуют явно названной совместимой обвязки GNU grep:
PCRE2-шаблон `first_byte(?=remaining_bytes)`, байты представлены как `\xHH`.
Например, `aaa`: `LC_ALL=C grep -aPob -e '\x61(?=\x61\x61)' fixture.bin`.
Он потребляет один байт и разрешает следующий старт через один байт; verifier
проверяет полную фразу. Возможность -P проверяется preflight на fixtures до замера.
Если системный grep этого не поддерживает, фиксируем конкретное ограничение,
не подменяем эталон обычным `-oF`. Многострочные/00-запросы вне первого опыта;
это ограничение области, не результат измеренного преимущества.

## Границы времени и памяти

Машина та же: i7-1355U, Ubuntu24.04 WSL, версии в ENVIRONMENT.json. Все компоненты
одного запроса (grep+wc/head/reducer тоже) на CPU0; наблюдатель на CPU1. Один поток,
OMP/BLAS=1. Docker/остальные среды включены; WSL не перезапускается. Не сбрасываем
OS page cache и не называем такие запуски физически cold I/O.

Основной вопрос — ПОСЛЕ загрузки готового индекса и проверки неизменного corpus:
start перед отправкой запроса -> JSON count/offsets + проверка байтов всех K позиций.
У GLYPH/Move-r процессы reader живут между запросами. GNU запускает штатный CLI
при каждом запросе; эта стоимость входит в его время. Записываем также число
процессов и стоимость запуска; не смешиваем её с чистым C++ kernel time.
Полный независимый oracle scan и запись журнала снаружи request timer, они проверяют
результат. Это НЕ время полного glyph-evidence verify-index/восстановления дерева.
Исходные corpus байты доступны локально всем для одинакового pread-bytecheck.
Хеши corpus/index закреплены до начала и сверяются между сериями; hash/loading
не переносятся в тёплое query время и показываются отдельно.

Дополнительно пять запусков свежего процесса для основного `(`/K10 на каждом
корпусе: отдельно setup SHA, загрузка reader, query+bytecheck, весь процесс до
проверенного JSON. Построение старого индекса не выдаётся за новый замер №4;
ссылочные времена №3 помечены контекстом. Сеть и передача архивов не измеряются.

RAM: loaded native RSS и wrapper RSS отдельно; VmHWM за всю жизнь процесса;
timestamped RSS семейства процессов с периодом10мс и видимым peak в окне запроса.
SUMRSS имеет повторно учтённые shared pages, это не physical/PSS. Порог ниже
относится к наблюдаемому RSS; очень короткий пик между отсчётами не исключается.
Для сравнения K0/K10 используем также свежие одинаково загруженные reader-процессы,
чтобы прошлый большой K не оставлял allocator cache. Наблюдатель и его файлы не
включаются в RAM участника. Отдельно учитываем bytes ответа и внутренних pipes.

## План и прогнозы ДО результата

Warmup: по одному K0 и K10 каждого запроса/движка; результаты тоже проверяются.
Основные замеры:30 кругов × четыре запросa × K0/K10 × два корпуса × GLYPH,
Move-r, GNU-stream, GNU-two-pass. Порядок циклический с обратным порядком нечётных
кругов; полная перестановка фиксируется runner-манифестом до первого замера.
Sensitivity K100/K1000/K65536 — пять кругов, отдельно от основного p95.
Oracle/версии/корпус/границы/лимиты после просмотра не меняются. Timeout300с на
одну попытку; timeout/сигнал/code/stdout/stderr и незавершённый процесс сохраняются,
не исчезают из журнала. Длинный этап — detached process с PID/status/log.

C (correctness): ноль расхождений count и координат, все байты PASS, все заявленные
отказы. Любое нарушение — FAIL и блок приёмки; время не оправдывает ошибку.

T (скорость): для каждого корпуса L(engine) — медиана четырёх per-query медиан
30 результатов K10. Прогноз: L(GLYPH) <= 0,5 × min(L(GNU-stream), L(GNU-two-pass))
на ОБОИХ корпусах. Нарушение хотя бы на одном — MISS; равенство порогу допустимо.
Move-r сравнивается по тем же p50/p95/отношениям; победитель GLYPH против Move-r
заранее открыт. Отдельно показываем каждую пару запросов, а не только агрегат.

M (память): на каждом корпусе для четырёх K10-запросов наблюдаемый native RSS peak
GLYPH над READY не больше16МиБ. Один больший пик — MISS. Загруженный индекс, wrapper
и стартовый peak показываются полностью; этот прогноз не утверждает totalRSS<16МиБ
или доказанную O(K)-память. Отдельно Δtime/ΔRSS K10−K0 и кривую по пяти K.

Вывод будущего отчёта: точный count, возвращено10, p50/p95, запросные/loaded/полные
RSS, bytes ответа/pipe, время setup/load/первого результата. Где быстрее/меньше
каждый инструмент и какая цена индекса. Публичные числа проверяет отдельный
контролёр. Пока этот опыт не запущен; публикация и выпуск — отдельное решение Якова.
