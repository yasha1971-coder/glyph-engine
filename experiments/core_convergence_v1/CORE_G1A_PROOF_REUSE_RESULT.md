## Exact limits: do not overclaim

- Proves only the narrow **claimed object's** exact literal occurrences under a receipt-bound V0 segment/root. Does not establish the completeness of all returned candidates across *every* committed segment or global absence.
- The receipt's root hash is a commitment to supplied root bytes, not independent evidence that the root is authoritative, current, signed or protected against rollback by a privileged writer.
- This does not certify anonymous cryptographic proof verification, authenticated suffix-order adjacency, production hostile-file parsing, or a zero-knowledge claim. \`verify_proof_carrying_recall_v0.py\` uses the source-available restorer and regenerates the full tiny corpus for its current verify path.
- The synthetic BWT/SA input was generated by a pure-Python oracle to the existing builders, not by the main native SA/BWT construction gate. This is intended for focused proof-bridge testing, not a replacement for P/R/O.
- There is no G1A full-store ratio, real-corpus startup latency or memory scaling result. Existing RLB3X 0.335 ratio belongs to a different 30-object historical scope.
- The existing V0 receipt alone is NOT the new normalized proof format. Avoid changing it without review and versioning.

## Decision from G1A

Stop inventing a parallel proof framework. CORE-G1B should reuse this established V0 proof path and reconcile it with portable O1–O6 evidence and frozen V1 Phase A/Phase B, without altering frozen contracts. The first hard new target is **proof-carrying compact storage at the 30-object public corpus**, with (a) exact identity and coverage, (b) independent replay against the compressed state after originals are unavailable, (c) the true total persistent size including every mandatory proof/rank/locate/restore artifact, (d) build/open memory and latency, (e) hostile mutations and absent/partial coverage distinctions.

If a trust boundary cannot be bridged without full materialization, declare that limitation as BLOCKED and propose the smallest new executable gate. A positive RLB3X test by itself must not become a claim of complete P/R/O/V1 integration.
